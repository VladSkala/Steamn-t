# PROJECT ROADMAP

Единый план доведения учебного проекта Steamn't до качественного завершённого состояния. Roadmap объединяет результаты аудита frontend/backend и сравнение текущей реализации со всеми дизайн-референсами из предоставленного `screens.zip`.

## Фактический статус приёмки (17 сентября 2026)

На PostgreSQL 16 в изолированном Docker-проекте прошли 265 backend-тестов. Проверены миграции и системные проверки. Frontend: 10 тестов, ESLint, production build. Дополнительно выполнены 111 HTTP-проверок сквозных сценариев и автоматизированная проверка 23 страниц на ширинах 1920, 1440, 1024, 768 и 390 (115 состояний). Подробности и ограничения — `docs/RELEASE_QA.md`.

Референсы из `screens.zip` просмотрены в контактных листах по всем десяти группам. Их геометрия используется как ориентир; по последнему требованию пользователя палитра фиолетовая. Попиксельное совпадение всех 106 состояний не заявляется. Исторические задачи сохраняются: checkbox отмечается только при подтверждении полного критерия. Наличие рабочей реализации не закрывает автоматически требование измеренного совпадения с Figma или полного аудита доступности.

## Правила работы по roadmap

- Выполнять задачи строго по порядку, если внутри задачи не указана независимость.
- Брать в работу один небольшой checkbox за раз.
- Не считать задачу готовой только потому, что написан код: должен выполняться указанный критерий готовности.
- Не удалять существующий пользовательский функционал. Противоречивые сценарии сначала переводить на единый контракт с сохранением данных и совместимости.
- Не придумывать новый дизайн. Главный визуальный эталон — геометрия изображений из `screens.zip`; палитра определяется последним требованием пользователя.
- Сохранять требуемую тёмную фиолетовую идентичность Steamn’t; референсы определяют композицию и пропорции.
- Не извлекать игровые изображения из скриншотов Figma. Использовать доступные проекту ассеты, повторяя пропорции, размеры и кадрирование.
- Все новые backend-возможности должны иметь проверки прав доступа и автоматические тесты.
- Все новые frontend-страницы должны иметь loading, error, empty и success-состояния, когда они применимы.
- После каждой завершённой задачи отмечать только соответствующий checkbox и записывать краткий результат в описание PR/рабочей сессии.

# Этап 1 — критические баги и сломанные сценарии

Цель этапа: стабилизировать контракты данных и основные пользовательские цепочки до добавления нового функционала.

## 1.1 Единый контракт Wishlist и Library Favorite

- [x] **[Frontend + Backend] Зафиксировать доменные правила Wishlist и Favorite.** Описать, что Wishlist содержит только ещё не купленные игры, после покупки запись удаляется, а Favorite относится только к Library. **Готово, когда:** правила однозначно отражены в API-контрактах, интерфейсных подписях и тестовых сценариях.
- [x] **[Backend] Привести wishlist endpoints к единому контракту.** Устранить противоречие между обычным Wishlist и toggle для уже купленной игры, сохранив совместимость существующих данных. **Готово, когда:** ни один endpoint не использует слово wishlist для library favorite и одинаковые действия дают одинаковый результат.
- [x] **[Backend] Проверить атомарное удаление игры из Wishlist после checkout.** **Готово, когда:** покупка и очистка Wishlist фиксируются одной транзакцией и откатываются вместе при ошибке.
- [x] **[Frontend] Привести все wishlist/favorite кнопки к соответствующим API.** Проверить Game Card, Game Details, Wishlist и Library. **Готово, когда:** состояние кнопок не расходится между страницами и сохраняется после refresh.
- [x] **[Frontend + Backend] Обработать duplicate и already-owned состояния.** **Готово, когда:** повторное нажатие не создаёт дубликаты, а пользователь получает понятное сообщение или актуальное состояние.
- [x] **[Backend] Добавить регрессионные тесты Wishlist/Favorite/Checkout.** **Готово, когда:** тесты покрывают добавление, удаление, повторный запрос, покупку, owned-конфликт и изоляцию пользователей.

## 1.2 Возврат после авторизации

- [x] **[Frontend] Ввести единый формат return location.** Передавать объект маршрута с `pathname`, `search` и `hash`, не смешивая его со строками. **Готово, когда:** все защищённые переходы используют один формат.
- [x] **[Frontend] Исправить Login redirect.** Восстанавливать полный исходный URL после успешного входа. **Готово, когда:** фильтры каталога, выбранная вкладка и hash не теряются.
- [x] **[Frontend] Исправить возврат после регистрации.** Если регистрация начата из защищённого сценария, возвращать пользователя туда же; иначе открывать профиль. **Готово, когда:** поведение регистрации и входа согласовано.
- [x] **[Frontend] Проверить auth redirect из Wishlist, Cart, Library, Community и реакций.** **Готово, когда:** после входа пользователь может продолжить исходное действие без повторного поиска страницы.
- [x] **[Frontend] Добавить проверки прямого открытия защищённых маршрутов.** **Готово, когда:** refresh и вставка URL в новую вкладку не приводят к неправильному маршруту.

## 1.3 Рабочие ссылки на публикации

- [x] **[Frontend + Backend] Выбрать канонический URL публикации.** Основной вариант — отдельный маршрут `/community/posts/:postId`; временные hash-ссылки должны корректно перенаправляться. **Готово, когда:** существует один устойчивый формат ссылки.
- [x] **[Frontend] Исправить Share для Community и Library Feed.** **Готово, когда:** скопированная ссылка открывает именно выбранную публикацию.
- [x] **[Frontend + Backend] Загружать публикацию отдельно от текущей страницы feed.** **Готово, когда:** пост открывается, даже если он не попал в первые результаты списка.
- [ ] **[Frontend] Восстанавливать открытые комментарии и фокус по deep link.** **Готово, когда:** ссылка на комментарии прокручивает страницу к нужному блоку и открывает его.
- [x] **[Frontend + Backend] Обработать удалённый, скрытый и недоступный пост.** **Готово, когда:** вместо пустого экрана показывается корректное 404/permission state.

## 1.4 Friendship и Follow

- [x] **[Frontend + Backend] Зафиксировать различие Friendship и Follow.** Friendship — взаимная дружба, Follow — односторонняя подписка. **Готово, когда:** модели, API, названия вкладок и счётчики используют эти определения.
- [x] **[Backend] Исправить вычисление profile counters.** **Готово, когда:** friends, followers и following считаются раздельно и не зависят от случайного источника данных.
- [x] **[Backend] Исправить источники Community и Library Feed.** **Готово, когда:** вкладка Following показывает подписки, Friends — принятых друзей, а смешанная выборка имеет отдельное честное название.
- [x] **[Frontend] Исправить подписи и ссылки в Profile, Friends и Feed.** **Готово, когда:** одинаковый счётчик в разных местах показывает одинаковое значение.
- [ ] **[Backend] Подготовить безопасную нормализацию существующих social-данных.** **Готово, когда:** миграция/команда не удаляет дружбу или подписки и допускает повторный запуск.
- [ ] **[Backend] Добавить тесты всех состояний связи.** **Готово, когда:** покрыты none, following, incoming, outgoing, accepted, blocked и self-action.

## 1.5 Просроченный JWT на публичных страницах

- [x] **[Frontend] Разделить публичные и защищённые API-запросы.** Публичный Catalog, Game Details и публичная Community не должны без необходимости зависеть от JWT. **Готово, когда:** старый токен не блокирует публичные данные.
- [x] **[Frontend] Исправить обработку неудачного refresh token.** После очистки токенов публичный запрос должен быть безопасно повторён без Authorization, если это допустимо. **Готово, когда:** пользователь остаётся на странице и видит публичный контент.
- [x] **[Frontend] Исключить циклы refresh/retry.** **Готово, когда:** каждый запрос повторяется не более одного раза и не создаёт бесконечных 401.
- [x] **[Frontend] Синхронизировать logout между вкладками и контекстами.** **Готово, когда:** Header, Cart и Wishlist сразу переходят в гостевое состояние.
- [x] **[Frontend] Добавить тестовые сценарии valid/expired/missing access и refresh token.** **Готово, когда:** результат каждого сценария предсказуем и документирован.

## 1.6 Целостность пользователей и покупок

- [x] **[Backend] Обеспечить регистронезависимую уникальность email.** **Готово, когда:** адреса, отличающиеся только регистром, не могут принадлежать разным пользователям даже при конкурентных запросах.
- [x] **[Backend] Определить и обеспечить регистронезависимую уникальность username.** **Готово, когда:** регистрация, login/search и база используют одно правило.
- [ ] **[Backend] Добавить безопасную миграционную проверку существующих дубликатов.** **Готово, когда:** потенциальные конфликты выявляются до установки ограничения и не теряются молча.
- [x] **[Backend] Исправить допустимый диапазон суммы заказа.** Согласовать максимальную цену игры, размер корзины и `Order.total_price`. **Готово, когда:** допустимая корзина не вызывает decimal overflow.
- [x] **[Backend] Защитить постоянное владение игрой от удаления Order.** Сохранить происхождение покупки, но не удалять LibraryItem каскадом. **Готово, когда:** завершённая покупка остаётся в Library после архивирования/удаления связанного заказа согласно принятой политике.
- [x] **[Backend] Проверить конкурентный checkout.** **Готово, когда:** два одновременных запроса не создают двойной заказ или двойное владение.
- [x] **[Backend] Добавить тесты ограничений базы и транзакций.** **Готово, когда:** тесты подтверждают ограничения на уровне БД, а не только serializer validation.

## 1.7 Приёмка критического этапа

- [x] **[Frontend + Backend] Пройти критический smoke-check.** Проверить auth return, Wishlist → Cart → Checkout → Library, post deep link и social-связи. **Готово, когда:** нет критических ошибок, 404, потери состояния или расхождения данных.
- [x] **[Frontend + Backend] Запустить lint, backend checks и полный текущий test suite.** **Готово, когда:** все проверки зелёные и новые регрессионные тесты включены в общий запуск.
